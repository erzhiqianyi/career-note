# 11 リスク・変更・コミュニケーション管理

状態：小規模 OSS の管理例。担当者名や承認を架空に記入しない。

## 役割と判断

| 判断 | 実行責任 | 判断・承認 | 相談先 |
| --- | --- | --- | --- |
| 目的・予算 | PM | プロダクト責任者 | 利用者 |
| 要件・受入条件 | 開発 / BA | 利用責任者 | QA / UX |
| 技術方式 | 開発 | メンテナー | セキュリティ |
| リリース | リリース担当 | メンテナー | QA / 運用 |
| 個人データの共有・削除 | データ所有者 | データ所有者 | 必要に応じ管理者 |

## 初期リスク台帳

| ID | リスク | 影響 / 優先 | 対策・残条件 |
| --- | --- | --- | --- |
| R-01 | 個人データが公開 Git に混入 | 大 / 最優先 | 外部保存、ステージ検査、ZIP 検査、実画面画像を公開しない |
| R-02 | 複数アカウントを独立したデータと誤認 | 大 / 高 | 単一ワークスペースを明記、許可対象を限定 |
| R-03 | import の部分書込み | 大 / 高 | バックアップ、分割、読戻し。原子化は今後の課題 |
| R-04 | 認証・Node・依存の仕様変化 | 中 / 高 | lockfile、CI、更新時テスト、既知脆弱性確認 |
| R-05 | AI の架空事実や求職ページの指示混入 | 大 / 高 | 原文出典、本人確認、不明点表示、応募を自動化しない |
| R-06 | 担当 1 名への依存 | 中 / 中 | 導入手順、ADR、復旧訓練、レビュー可能な PR |

担当・期限・最新状態は Issue に記録する。初期台帳だけでリスク対応済みにしない。

## 変更要求の流れ

要望 → 要件 ID と影響確認 → 工数・予算・日程・データの評価 → 判断 → 実装・試験 → 文書更新。緊急修正でも後から理由と検証を残す。対象外とした公開 SaaS を「設定変更だけ」で追加しない。

## コミュニケーション

週次の例：完了した成果、次週、障害・リスク、必要な判断を 1 ページにまとめる。会議は目的と決定事項、担当、期日を残す。決まっていないものを「了承」と記録しない。

受託や組織内導入の場合は、調達方針、RFP / 提案比較、契約範囲、検収基準、資産管理、教育計画を追加する。OSS 利用者が自分の PC で試すだけなら、同じ内容を短い導入チェックリストにまとめてよい。
