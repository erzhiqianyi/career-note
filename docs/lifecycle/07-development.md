# 07 開発・構成管理計画

状態：公開後の開発ルール。

## 変更単位

Issue に背景、再現手順または要件 ID、完了条件を記載する。小さなブランチを作り、コード・対応テスト・文書を同じ PR に含める。ブランチ名の例は `codex/fr-09-portable-startup`。main を直接書き換えず、通常は PR でレビューする。初回公開は既存コードを整理した初期コミットとして扱う。

## 標準手順

```sh
npm ci
npm test
npm run typecheck
npm run check:docs
npm run build
```

起動は `npm run dev`。スキル資料を変えたら `npm run skills:archive` を実行する。`npm run lint` は既存の厳格なルールも評価する。現在の未解消指摘は既知課題として扱い、新規コードに増やさない。成功していない検査を CI で成功したことにしない。

## レビュー観点

- 要件とコードが対応しているか。実装されていないことを文書が約束していないか。
- 実データや個人パスがテスト・サンプル・画像・ZIP に混ざらないか。
- 失敗時に個人の原回答や既存資料を失わないか。
- 外部サービスとデータ送信範囲が変わらないか。
- リリース後に元へ戻す方法があるか。

依存更新は lockfile を含める。大きな更新は既知の脆弱性と動作互換性を分けて判断する。自動 `audit fix --force` は互換性確認の代わりにならない。

## 構成とバージョン

ソース、文書、サンプル、図は Git。`.env`、`.dev.vars`、データベース、実際の import、バックアップは Git 外。公開前に `git diff --cached` と `npm run check:public` を確認する。

v0.x は互換性が変わり得るプレビュー。タグと CHANGELOG に変更範囲、移行要否、検証範囲を記録する。依存のライセンスは各パッケージに従う。
