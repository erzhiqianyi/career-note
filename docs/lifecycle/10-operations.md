# 10 運用・保守・廃止

状態：単一 PC のローカル運用手順。クラウド監視や可用性 SLA は提供しない。

## 日常運用

- 起動：`npm run dev`。停止：同じターミナルで Ctrl+C。
- 疎通：`npm run doctor`。画面、Worker、プロキシが応答することを確認。
- 保存：編集後に再表示し、重要な資料は必要に応じて個別 export。
- 定期：依存更新、空き容量、不要な Agent トークンの失効、バックアップ復旧試験。

## バックアップと復旧

**両サービス停止中に `CAREER_DATA_DIR/worker-state/` 全体をコピーする。** 内部 SQLite ファイルだけを、稼働中に抜き出してバックアップにしない。`.env` と `.dev.vars` は別途安全に保管する。バックアップ先はソースリポジトリ外で、個人データとして扱う。

macOS / Linux / WSL2 の新規既定保存先を使う例：

```sh
# 必ず先に Ctrl+C でサービスを止める
mkdir -p "$HOME/career-note-backups"
cp -R "$HOME/.local/share/career-note/worker-state" \
  "$HOME/career-note-backups/worker-state-$(date +%Y%m%d-%H%M%S)"
```

カスタム `CAREER_DATA_DIR` を使っている場合はコピー元を置き換える。復旧はバックアップを新しい空の親ディレクトリの `worker-state/` にコピーし、その親を `.env` に指定する。再起動後、プロフィール・求人 ID・資料件数を確認する。失敗した元データは検証が済むまで保持する。

Web の JSON export は閲覧・持出し用の状態スナップショット。`/import` は完全復元 API ではなく、profile・元回答・トークンを含む DB 全体の復元に使えない。

目標例：作業終了時に日次コピー、重要変更前に追加コピー、月次で別保存先への復旧を試す。RPO 1 日 / RTO 1 時間は導入者が検証して決める目標であり、本製品の保証値ではない。

## 障害一次対応

| 症状 | 対応 |
| --- | --- |
| ページが開かない | doctor、起動ログ、ポート競合を確認。無関係なプロセスは停止しない |
| API だけ失敗 | Worker 設定、ポート、D1 保存先を確認 |
| Google 認証失敗 | Firebase provider、localhost、Web 設定、許可リストを確認 |
| import が途中で失敗 | state で書込み済み ID を確認し、残りだけを整理。盲目の再送を避ける |
| トークン漏えい疑い | 該当 Agent トークンを失効。必要に応じて秘密を更新し影響調査 |
| データ消失の疑い | 書込み停止、現物保全、別保存先へ復旧。公開 Issue に DB を添付しない |

## 保守と廃止

更新履歴、依存、データ形式の変更を確認し、変更前バックアップを行う。利用終了時は必要な資料を export し、バックアップの保持期間を決め、サービスを停止し、連携トークンを失効する。データ削除は所有者が対象を確認して行う。ソースフォルダー削除だけでは外部データは消えない。Firebase のユーザー削除とローカル資料削除も別操作。
