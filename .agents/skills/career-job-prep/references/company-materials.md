# 公司材料与面试题

选定目标岗位后读取。字段与保存协议以项目 `docs/agent-workflow.md` 为准；此文件说明选材和内容质量，不复制 JSON schema。

## 先建立要求与证据的对应

每个重点要求对应：招聘原文与链接 → 个人事实来源 → 本人职责和行动 → 结果及范围 → 拟放入的材料 → 可能追问。

优先选取少数最有说服力的经历：既能说明岗位要求，也能讲清本人实际做了什么。案例中的业务背景、方案取舍与验证过程比增加技术名词更有用。

核对以下容易被改写放大的地方：

- 雇主与客户项目、正式职称与实际技术职责、个人行动与团队成果。
- 单次任务结果与整个框架规模、手工工时与自动执行耗时、POC 与正式系统交付周期。
- 原始业务证据、本人回忆、本人公开网站重复表达、Agent 提炼的不同证明强度。
- 个人项目的设计、实现、测试、发布、用户规模；过去的发布计划不成为已发布事实。
- 中文与日文中的日期、数字和职责必须一致。无法补充的历史数字可保留边界，不反复要求本人找已不可获取的资料。

## 五类独立材料

| 类型 | 必须解决的问题 |
| --- | --- |
| 公司研究 | 公司业务、实际岗位、为什么可能匹配、证据对应、缺口与要向企业确认的事项 |
| 履歴書 | 已确认的基本信息、学历、资格与任职时间线，遵守本人联系方式和私密信息边界；缺失字段留待填写 |
| 職務経歴書 | 岗位适配的职业摘要、相关职责、代表案例、成果口径、技能使用场景与个人贡献 |
| 志望動機 | 对该公司具体业务/岗位的理解、相关经历能如何贡献、本人确认的职业方向；不编造长期仰慕或私人动机 |
| 面试准备 | 60秒自我介绍参考、2–3个可讲案例、技术追问、日语表达、逆質問、分轮练习计划 |

每类以独立新版本保存，正文可读，来源与待确认项写入 `sourceNotes`。公司专属不是在通用文稿里换公司名；正式简历选择重点，完整事实和多版本案例留在外部原始素材中。

工作区默认可直接保存 Markdown。用户要求 PDF/DOCX 时才额外采用对应可用文档技能排版和渲染检查；未请求时不引入外部模板账号或上传个人资料。

## 面试练习题组

按工作流生成约8–15题，数量与本轮范围、岗位复杂度相称；样板可以更少，但要说明样板范围。每题具备：

- 自然日语问题、中文含义、语义一致的简单日语版本。
- 与本公司岗位及所选个人证据有关的出题理由。
- 背景→本人行动→验证→结果的回答结构，必要时列出事实缺口。
- 2–3条具体追问；追问应深入本题行动、取舍或证据，而不是通用问题重复。
- 合理建议时长、关键词读音和解释。

`candidateContext` 使用当前确认的海外经验、学习与求职背景，不能固化某次样板的姓名、年限、证件或公司。`communicationGuide` 说明先构思、再短句日语、再追问的练法，以及如何澄清没听懂的部分。

优先考虑与本人情况有关的海外雇主关系说明、赴日/转职动机、工作日语、入职条件、技术沟通及逆質問。不因为外国身份一律要求解释私人家庭、国籍文化或承诺永不离日。日语自然度与专业能力分别判断，JLPT 不是口语实测。

参考答案明确标为练习用改写，不能保存为真实 `attempts`。对本人动机或事实缺口，提供组织结构或待填位置，不代替本人补出经历。带 `candidateContext` 的真实回答点评要包含 `foreignApplicantNotes` 与 `simpleAnswer`，其余点评流程见项目工作流。

## 完成前检查

- 选定公司与职位唯一明确；招聘关键条件按本轮来源核验。
- 正文的个人行动、数字、雇主关系可追溯，推演与待确认部分有清楚标记。
- 整套准备的五类材料齐全，题组关联同一岗位；若用户仅要部分，不标记整套公司准备任务完成。
- 材料和题组有全新 id；旧履历、旧题组、真实回答与投递状态保留。
- 已按请求范围完成 preview 或 import/readback。网络失败或证据缺失时如实交代实际完成部分。
